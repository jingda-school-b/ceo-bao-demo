# 配送地址围栏判定 · 演示

同城配送场景下的一个小问题：**一个地址，究竟该归哪条配送线路？**

系统用「围栏 + 点面判定」来回答：每条线路对应地图上的一个多边形围栏，
把地址解析成经纬度后，判断点落在哪个多边形内。本仓库是该思路的**可运行演示版**。

## 演示什么

| 能看 | 看不到 |
|---|---|
| 射线法（Ray Casting）点面判定的完整实现 | 生产的候选召回策略与多级匹配规则 |
| 名称归一化 + 二元组 Dice 相似度 | 地址门牌三态校验、唯一线路兜底等业务逻辑 |
| 客户端 Canvas 现场画围栏、标点 | 地图 API 接入、缓存、数据库、管理后台 |
| 一条可执行命令跑起来的 Web 演示 | 任何真实客户数据、密钥、线路配置 |

数据全部虚构（`data/` 下的三个片区、十个地点），不含任何真实信息。

## 算法要点

**为什么用射线法而不是「包围盒 + 质心距离」**：配送围栏经常是不规则多边形
（沿道路、河道、铁路切分），包围盒会把圈外的点误判进来，质心距离在长条形
围栏上误差更大。射线法能严格处理凹多边形。

两个容易写错的地方：

1. **射线穿过顶点**：用 `(yi > y) != (yj > y)` 这种半开区间写法，保证每个顶点
   只被计算一次，否则会把「交点」重复计数，导致内外翻转。
2. **点落在边上**：射线法对边界点的结果不稳定，需要单独做点到线段距离判断。

**为什么用 Dice 而不是编辑距离**：门店名普遍很短（4~8 字），编辑距离对
「多一个字 / 少一个字」过于敏感；二元组 Dice 对短文本更稳，且计算量小。
